2024 年我做了一个叫 myAgent 的项目——"AI Agent 智能应用从 0 到 1 定制开发"，做完第一版就搁下了。现在回头看，第一版恰好卡在所有教程的同一个终点上：能跑，但不知道为什么这么搭。这次重构系列，就从回答那个最根本的问题开始。

## 1 第一版的问题出在哪

第一版的 myAgent 是典型的"教程终点站"形态：一个主循环 + prompt 模板 + 工具调用的 if-else。它有三个具体毛病：

1. **工具调用是硬编码的**——加一个工具要同时改三处：注册表、prompt 描述、分发逻辑
2. **没有记忆结构**——多轮对话就是把历史整个塞进 context，token 花得越来越多，信息密度越来越低
3. **不可观测**——Agent 决策错了，没有任何日志能告诉我它是"想错了"还是"拿到了错的观察"

这三个毛病指向同一件事：我把 Agent 当成了一个功能，而不是一个系统。

## 2 为什么不套框架

重构前认真比较过三条路：LangChain / LangGraph、Dify 这类低代码平台、从零写。结论是从零写，理由有三：

**一，框架藏住的恰恰是要学的东西。** LangChain 把 ReAct 循环、工具分发、记忆管理全封装了，用起来快，但"Agent 为什么这样决策"这个核心问题被框架吃掉了。myAgent 这个项目的立身之本就是"从 0 到 1 定制"，套框架等于把项目灵魂卖了换速度。

**二，抽象层有自己的税。** 框架的抽象为了通用性会引入间接层。教程规模的 demo 感觉不到，一旦要做定制化的反思机制或特殊记忆结构，就是和框架的抽象搏斗。从零写的东西，改起来只有我自己的约束。

**三，LLM API 本身已经是"框架"了。** 2026 年的模型 API 原生支持 function calling、结构化输出，当年框架解决的那层胶水，平台层已经吃掉了大半。裸写的成本比两年前低很多。

> 不从零写也不丢人——如果目标是两周上线一个客服机器人，Dify 是正确答案。但从零写的目标是**理解**，目标不同，路线就不同。

## 3 重构路线：四步

这次重构定了四步，每步都有明确的"完成定义"：

### 第一步：循环骨架
把 ReAct 循环写干净：思考 → 行动 → 观察，最大步数熔断，超时退出。完成定义：一个"查天气再总结"的双工具任务能稳定跑通，且每一步的中间产物都落日志。

### 第二步：工具系统
工具改成声明式注册——一个装饰器同时解决注册、schema 生成、prompt 描述注入三件事。加新工具只写一个函数。完成定义：加一个新工具的改动量 ≤ 10 行（不含工具本身逻辑）。

### 第三步：记忆结构
把"对话历史全量塞入"改成分层：工作记忆（当前任务的 scratchpad）+ 情景记忆（按任务归档）+ 摘要（超长时压缩）。完成定义：50 轮对话后，token 消耗增速显著低于线性，且关键事实不丢。

### 第四步：可观测
每个决策点记录：模型看到了什么、输出了什么、工具返回了什么。复盘时能回答"这一步它为什么这么选"。完成定义：给一个失败 case，能在日志里定位到具体的决策步。

## 4 一个预先的约定

吸取博客重构的经验，规矩先立好：

- 每步完成必须有可运行的验收脚本，报数字，不许"应该没问题"
- 每步写一篇笔记（就是本系列），写不清楚的说明没做透
- 不追新——中途出了新的框架/模型不换路线，记进待办下一轮再说

四步走完，myAgent 就不再是教程复刻，而是一个我能解释每一个设计决策的、自己的 Agent。下一篇从循环骨架开始。
