## 它解决什么问题

字典已经能按名字取东西了，但它把这件事交给了对象的内部实现，看不见也摸不着。散列表把这个过程摊开来讲：

**给每个键算出一个数字，拿这个数字当数组下标。**

这样一来，找东西只要两步：算一次，取一次。不用遍历，不用比较。这就是它能做到常数时间的原因。

## 生活里长什么样

图书馆用书名首字的笔画数决定放哪个书架。找书的时候先算笔画数，直接走到那个书架，不用从第一排开始翻。

但可能会遇到两本书笔画数一样，都该放第三个书架。这就是冲突，散列表有一半的篇幅在讲怎么处理它。

## 一步步写

### 第 1 步 一个数组当容器

```js
function HashTable() {
    var table = [];
}
```

其他结构和这里都一样，底下都是数组或者对象，区别在**怎么算下标**。

### 第 2 步 写散列函数

这是散列表的核心。它把任意长度的字符串压成一个固定范围内的整数。

```js
var loseloseHashCode = function (key) {
    var hash = 0;
    for (var i = 0; i < key.length; i++) {
        // 获取 ASCII 码值
        hash += key.charCodeAt(i);
    }
    // 哈希值和一个任意数做除法取余
    return hash % 37;
};
```

分开看就两件事：

1. `charCodeAt(i)` 拿到每个字符的编码，累加起来
2. `% 37` 把结果压进 0 到 36 这个范围

乘积累加是一种常见做法，能减少不同顺序的字符串算出同一个值的概率。这里用的是最简单的一份，所以名字里带 `lose`。

比例关系要记住：**余数决定了数组要用多大**。写 `% 37`，那这个散列表最多放 37 个位置。位置太少冲突就多，位置太多就是浪费内存，这个取舍要按实际数据量来定。

### 第 3 步 存

```js
this.put = function (key, value) {
    var position = loseloseHashCode(key);
    console.log(position + ' - ' + key);
    table[position] = value;
};
```

那句 `console.log` 是当年调试留下的，正好能看见每个键被算到了哪个位置。演示页上会直接显示出来。

注意这里**只存了值，没存键**。这是个隐患，后面会说到。

### 第 4 步 取

```js
this.get = function (key) {
    return table[loseloseHashCode(key)];
};
```

同一个键走同一个散列函数，一定算出同一个位置，所以直接取就行。这就是散列表快的全部秘密。

### 第 5 步 删

```js
this.remove = function (key) {
    table[loseloseHashCode(key)] = undefined;
};
```

源码里特意留了一段注释解释这里为什么不真的 `delete`：散列表里元素散落在整个数组中，很多位置本来就是空的，值为 `undefined` 就表示这个位置没东西。所以赋 `undefined` 的效果和删除一样。

### 第 6 步 冲突了怎么办

假设这样一组数据：

```
Jonathan -> 5
Jamie    -> 5
```

两个不同的名字算出了同一个位置。直接 `table[5] = value` 的话，后写的会把先写的覆盖掉，数据就丢了。

书里给了两种解法，这份仓库里两种都写了：

**分离链接**：让每个位置都挂一条链表，撞在一起的就挂在同一条链上。

```js

```

**线性探测**：位置被占了就往后找，找到第一个空位放进去。

```js
// hash/LinearProbing.js
```

两种都能看演示。分离链接的演示页里能看到撞车的键排在同一条链上。线性探测那个页面当年脚本没写完，打开是空的，只能直接读 `hash/LinearProbing.js`。

顺带说一个必然的结论：这个散列函数把每个字符的编码加起来，所以**只要字符相同、顺序不同，算出来的值一定相同**。`abc`、`bac`、`cab` 会撞在同一个位置。

这就是加法当散列函数的短板。真正好用的散列函数会把乘法和位移混进来，让顺序也参与运算。

## 复杂度

| 操作 | 平均 | 最坏 | 说明 |
|---|---|---|---|
| put | O(1) | O(n) | 冲突全撞一起时，分离链接会退化成链表遍历 |
| get | O(1) | O(n) | 同上 |
| remove | O(1) | O(n) | 同上 |

一个散列函数好不好，主要看两件事：算得快不快，算出来的分布匀不匀。分布不均的话，有的位置堆一堆，有的位置空着，平均值就被拉垮了。

## 什么时候会用到

- 各种语言的字典、Map、对象底层
- 缓存：把请求参数算成键，命中就直接返回
- 去重、计数
- 数据库索引

## 容易踩的坑

- **只存值不存键**。这份实现就没存键，导致 `put(1, 'a')` 和 `put('1', 'b')` 存的是同一个位置，还分不清谁是谁。真实实现里每个位置存的都是「键值对」，取的时候要再核对一次键是否相同
- 数组大小和取余的模数不一致。写 `% 37` 就要清楚这意味着 37 个位置，别自己搞混
- 以为换个更大的数组冲突就没了。模数变大只是把冲突摊薄，撞车这件事本身消除不掉，冲突处理那一步必须写
