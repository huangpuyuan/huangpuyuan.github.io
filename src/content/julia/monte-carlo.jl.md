## 问题

从 `[0, 1)` 的均匀分布里抽 500 个数，求平均。把这件事重复 **100 万次**，得到 100 万个均值。

问：这 100 万个均值**分布长什么样**？

原始分布是平的（均匀分布），完全不像钟形。但答案很反直觉——这些均值会乖乖排成一条**正态曲线**。

## 中心极限定理

这就是**中心极限定理（CLT）**：不管原始分布是什么形状，**只要样本量够大，样本均值的分布就趋近正态分布**。

注意关键点：**原始分布不需要是正态的**。这里原始分布是平的，照样成立。这就是它为什么是统计推断里最重要的定理——它允许你在不知道总体分布的情况下，用正态分布的性质做推断。

代码验证的思路很直接：

```julia
const REPEATS = 10^6
const SAMPLE = 5 * 10^2

rng = MersenneTwister(42)
data = [mean(rand(rng, SAMPLE)) for _ in 1:REPEATS]
lo, hi = quantile(data, 0.01), quantile(data, 0.99)
```

`rand(rng, SAMPLE)` 一次生成 500 个随机数，`mean` 求平均，外面套数组推导式重复 100 万次。然后取 **1% 分位数**和 **99% 分位数**——如果数据真的服从正态分布，这两个分位点之间应该正好盖住 **98%** 的样本。

## 理论宽度能提前算出来

不用跑程序，光靠公式就能知道区间应该是多宽：

1. 均匀分布 `[0, 1)` 的方差是 `1/12 ≈ 0.0833`
2. 500 个样本的均值，标准差是 `√(1/12 / 500) ≈ 0.0129`
3. 正态分布 1% ~ 99% 对应 **±2.326 个标准差**，全宽约 `2 × 2.326 × 0.0129 ≈ 0.0601`

```julia
@printf("理论宽度 ≈ 2 × 2.326 × sqrt(1/12/%d) = %.4f\n",
        SAMPLE, 2 * 2.326 * sqrt(1/12/SAMPLE))
```

第 2 步用到的性质是：**样本均值的方差 = 总体方差 / 样本量**。样本量从 500 涨到 50000，均值分布的宽度会缩到 1/10——这就是「数据越多，估计越准」的数学形式。

## 性能实测

同一个计算，用两种写法：

**慢写法**——先建空数组，再往进塞：

```julia
data = Float64[]
for _ in 1:REPEATS
    group = Float64[]
    for _ in 1:SAMPLE
        push!(group, rand(rng))
    end
    push!(data, mean(group))
end
```

**快写法**——数组推导式一行搞定：

```julia
data = [mean(rand(rng, SAMPLE)) for _ in 1:REPEATS]
```

实测：

```
慢写法（push!）：98% 的均值落在 (0.4700, 0.5300)，宽度 0.0600
 19.895 seconds (506.37 M allocations: 14.704 GiB)

快写法（推导式）：98% 的均值落在 (0.4700, 0.5301)，宽度 0.0601
  1.185 seconds (2.10 M allocations: 3.919 GiB)

理论宽度 ≈ 2 × 2.326 × sqrt(1/12/500) = 0.0601
```

**19.9 秒 vs 1.19 秒，快 16.8 倍。**

## 为什么差这么多

看括号里那行数字就明白了：

| | 耗时 | 内存分配次数 | 分配总量 |
|---|---|---|---|
| push! | 19.90 s | **506 M** | 14.7 GiB |
| 推导式 | 1.19 s | **2.1 M** | 3.9 GiB |

差距的根源是 **`push!` 不断触发内存扩容**。

`push!(group, rand(rng))` 每加一个元素，都要检查容量够不够；不够就重新分配一块更大的内存、把老数据搬过去。跑 100 万次外循环 × 500 次内循环 = **5 亿次 push**，其中相当一部分都伴随扩容和搬运。

而 `rand(rng, SAMPLE)` **一次性生成 500 个数**——它事先就知道要生成多少，直接分配好一整块内存填进去，不需要边跑边扩。

`Float64[]` 这个写法也值得说：推断出**空数组的元素类型是 Float64**。类型明确的数组在 Julia 里是连续内存块，访问极快；如果类型不确定（比如 `[]` 得到 `Any[]`），就会退化成装指针的盒子，性能差一个数量级。

## 三条能带走的经验

1. **能一次生成，就别一个一个塞。** `rand(rng, n)` 比循环 `push!` 快得多，`[f(i) for i in 1:n]` 比 `push!` 快得多。
2. **数组要标类型。** `Float64[]` 不是啰嗦，是让编译器知道内存怎么排。
3. **从 Python 带过来的习惯在 Julia 里经常是反的。** Python 里 `push!` 是标准做法（列表是动态数组的天然形态），Julia 里它是有代价的。**换语言的时候，最该重学的是「习惯写法」，而不是语法。**

顺带一提：即使快写法里有 26.58% 的时间花在 GC 上（生成 1TB 级数据总要回收），它还是把慢写法甩开了 16 倍。**内存分配次数才是 Julia 性能的头号敌人。**
